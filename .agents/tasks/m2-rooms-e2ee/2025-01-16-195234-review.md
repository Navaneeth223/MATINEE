# M2: Rooms + E2EE + Presence + Invite

This milestone implements the foundation for secure multi-peer rooms: room creation with invite URLs, end-to-end encryption using ECDH key exchange, peer presence broadcasting, and a waiting room UI. The implementation spans backend infrastructure (Cloudflare Workers + Durable Objects), cryptographic primitives (ECDH P-256, AES-GCM-256), client-side room management, and React UI components.

Four features were implemented: backend room API with presence broadcasts (FEAT-001), E2EE crypto layer (FEAT-002), RoomClient library with automatic key exchange (FEAT-003), and waiting room UI with real-time peer list (FEAT-004). TypeScript compilation passes cleanly across all packages (edge, protocol, web). Manual browser testing is pending but all automated verification criteria are met.

**Watch for:** Key exchange race condition when peers join simultaneously (likely); missing encryption for actual message payloads beyond key-exchange (confirmed); WebSocket readyState checks use numeric literals instead of constants (confirmed); no reconnection logic for dropped connections (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

E2EE key exchange happens automatically on connection: each peer generates an ECDH P-256 key pair, broadcasts their public key, derives shared secrets using HKDF-SHA-256 with roomId as salt, and signals 'ready' when all peer keys are exchanged. The roomId salt ensures different rooms produce different keys even with identical peer key pairs. The crypto layer exports six functions (generateKeyPair, exportPublicKey, importPublicKey, deriveSharedSecret, encryptMessage, decryptMessage) and includes a test harness that verifies round-trip encryption and room isolation.

Presence is broadcast bidirectionally: when a new peer connects, the server sends them the list of existing peers, then broadcasts peer-joined to all existing peers. On disconnect (close or error), the server broadcasts peer-left before removing the session. The Durable Object tracks sessions using serializeAttachment/deserializeAttachment for hibernation compatibility.

RoomClient manages the full WebSocket lifecycle: it generates a peerId, connects to ws://localhost:8787/ws/{roomId}, automatically initiates key exchange, listens for presence events, and maintains local state (peers array, sharedKeys map). It exposes an event emitter API (on/emit pattern) with six events: connected, peer-joined, peer-left, ready, disconnected, error. The sendMessage method supports optional per-message encryption but the current implementation only encrypts with the first shared key, not per-peer.

The waiting room UI (RoomPage) displays room ID, invite URL with clipboard copy, a color-coded connection status badge (red → yellow → blue → green for disconnected → connecting → connected → ready), and a real-time peer list showing display names and join times. Navigation flows from FoyerPage (POST /api/rooms) → /room/:roomId (waiting room) → /theatre/:roomId (playback, deferred to M3+).

## Issues (8)

1. **Key exchange race on simultaneous join** — When two peers connect at nearly the same time, each may check `sharedKeys.size === peers.length` before the other's peer-joined event has updated the peers array, causing both to think they're ready when they're not. The condition should either compare against expected peer count from the server's initial peer list or delay the ready check until all peer-joined events have fired.

2. **sendMessage encrypts only with first shared key** — The current implementation encrypts broadcast messages using `sharedKeys.values().next().value` (the first key in the map). Multi-peer rooms (>2 participants) will fail to decrypt because each peer has a different shared secret. Implement per-peer encryption: iterate over sharedKeys, encrypt the payload once for each peer's key, and send individual messages or use a hybrid approach (symmetric session key encrypted per-peer + bulk data encrypted once).

3. **WebSocket readyState uses magic numbers** — Both room-do.ts and room-client.ts check `other.readyState === 1` (OPEN state). Use WebSocket.READY_STATE_OPEN constant or the spec-standard WebSocket.OPEN if available in the Cloudflare Workers runtime. This improves readability and prevents errors if numeric values change.

4. **No reconnection logic** — When the WebSocket disconnects (network drop, server restart, room expiry), RoomClient emits 'disconnected' but does not attempt to reconnect. FR-104 requires reconnection with exponential back-off and 5-minute state preservation. Add reconnection state machine to RoomClient: track attempt count, implement exponential back-off (e.g., 1s, 2s, 4s, 8s, max 30s), and give up after 5 minutes or when server returns permanent failure.

5. **Room expiry (FR-103) not implemented** — Requirements specify 30-minute inactivity cleanup using Durable Object alarms. RoomDO has no alarm() method and no inactivity tracking. Add a scheduled alarm that checks last activity timestamp and closes all sessions if exceeded.

6. **No clipboard API fallback** — The invite URL copy button uses navigator.clipboard.writeText, which requires a secure context (HTTPS or localhost) and isn't supported in older browsers. Add fallback for unsupported browsers (select + document.execCommand('copy')).

7. **Hardcoded API origin in FoyerPage** — FoyerPage POSTs to `http://localhost:8787/api/rooms` (hardcoded). This will break when deployed. Use `window.location.origin` or an environment variable for the API base URL.

8. **Message validation missing** — The Durable Object doesn't validate message schemas. If a client sends malformed JSON or a message with type='key-exchange' but invalid payload, the DO relays it to all peers. Recipients might crash or ignore it. Add JSON schema validation to prevent malicious/buggy clients from disrupting peers.

## Transport abstraction via Stream interface

The protocol package defines WSMessage with a discriminated union type (WSMessageType) covering room lifecycle (join, leave), sync (sync, chat), WebRTC signaling (ice, signal), heartbeat (ping, pong), and the new M2 types (peer-joined, peer-left, key-exchange). Every message carries roomId, peerId, and optional payload. The server-side Durable Object relays messages to all peers except the sender, preserving peerId so recipients know the origin.

WebSocket connections upgrade at `/ws/{roomId}?peerId={...}&name={...}`. The DO accepts the WebSocket, extracts query params, creates a Peer object (id, displayName, joinedAt), and stores it using serializeAttachment for hibernation. The DO's webSocketMessage handler parses incoming JSON, special-cases key-exchange to relay without storage, and broadcasts everything else. This design keeps the server stateless for message content—it's a blind relay.

The choice to send peer-joined messages individually (one per existing peer) rather than a single "here are all peers" message increases message volume but simplifies the protocol: the client uses the same peer-joined handler for both initial state and subsequent joins. A single "peer-list" message would reduce round-trips for rooms with many peers but adds another message type.

## E2EE handshake and key derivation

Key exchange uses ECDH P-256 (crypto.subtle.generateKey with 'ECDH' and 'P-256' curve). Each peer generates a key pair on connect, exports the public key as JWK (exportPublicKey), and broadcasts it in a key-exchange message. When a peer receives a key-exchange, it imports the peer's public key (importPublicKey) and calls deriveSharedSecret, which:

1. Derives 256 bits using ECDH (crypto.subtle.deriveBits)
2. Imports those bits as an HKDF key
3. Applies HKDF-SHA-256 with roomId as salt and empty info
4. Outputs an AES-GCM-256 key

The roomId salt is critical: without it, two peers who connect to different rooms would derive the same shared secret, allowing cross-room decryption.

Encryption generates a random 12-byte IV (crypto.getRandomValues), encrypts with AES-GCM (which embeds a 16-byte authentication tag in the ciphertext), and returns an EncryptedEnvelope with base64-encoded iv and ciphertext. If the ciphertext is tampered with or the key is wrong, decrypt throws, which the caller must handle.

The test harness (__test-e2ee__.ts) tests room isolation: derives a key for a different roomId and confirms that decryption fails. It doesn't test the integration with RoomClient (that requires manual browser testing per FEAT-003).

## RoomClient state machine and event lifecycle

RoomClient's connection state progresses: disconnected → connecting (after generateKeyPair, before WebSocket open) → connected (onopen fires) → ready (after all peer keys exchanged).

On connect(), RoomClient generates a key pair, opens WebSocket to `ws://localhost:8787/ws/${roomId}?peerId=${peerId}&name=${displayName}`, and sets up event handlers. The onopen handler broadcasts the key-exchange message and emits 'connected'. The onmessage handler routes by message type:

- key-exchange: imports peer public key, derives shared secret, stores in sharedKeys map, checks if all keys exchanged (sharedKeys.size === peers.length), emits 'ready' if yes
- peer-joined: adds peer to local peers array (filtering out self), updates roomStore, emits 'peer-joined', re-broadcasts own public key to the new peer
- peer-left: removes peer from peers array, deletes from sharedKeys, updates roomStore, emits 'peer-left'
- other types: emits 'message' event (no decryption yet)

The re-broadcast of own public key on peer-joined is necessary because the new peer doesn't have your key yet.

The sendMessage method checks `this.ws.readyState !== WebSocket.OPEN` before sending. If encrypt=true and connectionState='ready', it serializes the payload to JSON, encrypts with "the first shared key," and wraps it in a WSMessage. This is a known gap (see Issues #2): it doesn't encrypt per-peer, so multi-peer rooms will break.

The disconnect() method closes the WebSocket, clears sharedKeys, clears peers, resets connectionState to 'disconnected'. It does not attempt reconnection.

## Waiting room UI and clipboard integration

RoomPage is a React component that mounts RoomClient on load. It extracts roomId from useParams, generates a peerId (crypto.randomUUID()), gets displayName from userPrefsStore (defaulting to 'Watcher'), constructs the invite URL (`${window.location.origin}/room/${roomId}`), and creates a RoomClient instance.

The useEffect cleanup function unsubscribes all event listeners and calls client.disconnect().

The invite URL copy button calls navigator.clipboard.writeText(inviteUrl) and shows green checkmark feedback for 2 seconds. No fallback exists for browsers that don't support Clipboard API.

FoyerPage's "Create Room" button POSTs to `http://localhost:8787/api/rooms` (hardcoded origin). This will break when deployed.

## Server-side presence and relay logic

The Durable Object's fetch method checks the Upgrade header, extracts peerId and name from query params, accepts the WebSocket, serializes the Peer object as attachment, and adds to the sessions map. Before returning the WebSocket response, it:

1. Constructs existingPeers array by filtering out the new peer's WebSocket
2. Sends each existing peer as a peer-joined message to the new peer (so they know who's already there)
3. Broadcasts a peer-joined message with the new peer's info to all existing peers

The broadcast uses `this.state.getWebSockets().forEach(other => { if (other !== server && other.readyState === 1) ... })`. This skips the new peer's own WebSocket and checks readyState to avoid sending to closing/closed sockets. The numeric literal `1` should be WebSocket.OPEN.

webSocketMessage checks msg.type === 'key-exchange' and relays those messages to all other peers without modification (other than injecting the sender's peerId from the attachment). Other message types are broadcast the same way. This means the server never stores message history—rooms are ephemeral.

webSocketClose and webSocketError are identical: extract peer from attachment, broadcast peer-left to remaining peers, delete from sessions map.

getCurrentPeers() is defined but never called.

## API surface and protocol contracts

POST /api/rooms returns `{ roomId: string, inviteUrl: string }`. The inviteUrl is constructed as `${url.origin}/room/${roomId}`, using the request's origin.

GET /api/ice returns `{ iceServers: [...] }` with STUN servers (stun.cloudflare.com:3478, stun.l.google.com:19302). STUN-only means direct P2P will work on most networks but will fail behind symmetric NATs.

The WebSocket endpoint is `/ws/{roomId}?peerId={peerId}&name={displayName}`. The peerId is client-generated (crypto.randomUUID()). If the client omits peerId, the server generates one, but RoomClient always provides it.

## Security and auth posture

E2EE is implemented for key exchange: peers derive shared secrets without the server seeing private keys. However, the actual message payloads (sync, chat, subtitle cues) are not yet encrypted—they're sent as plaintext JSON. The sendMessage method has an encrypt parameter but no message types use it yet. This violates FR-702 ("All room messages encrypted before leaving browser") and FR-703 ("no server plaintext").

Public keys are transmitted in plaintext (key-exchange messages). This is inherent to ECDH—public keys are public. An attacker observing the WebSocket can't derive the shared secret without a private key.

There is no authentication: anyone with a room URL can join. Room IDs are UUIDs (~122 bits of entropy). If a room URL leaks, it's compromised.

The Durable Object doesn't validate message schemas. Malformed messages are relayed to peers, who might crash or ignore them.

## Resource management and lifecycle

RoomClient creates a WebSocket in connect() and closes it in disconnect(). The Durable Object stores sessions in a Map<WebSocket, Peer> and removes entries on close/error.

Room expiry (FR-103) is not implemented. Without an alarm, rooms never clean up even if all peers disconnect. The sessions map becomes empty, but the DO remains allocated. Cloudflare bills for DO duration (free tier: 400,000 GB-seconds/month), so abandoned rooms consume quota. Implementing the alarm is a must-fix for production but not blocking for local dev testing.

The crypto primitives don't store keys persistently—they're CryptoKey objects in memory. When the page reloads, key exchange starts fresh.

## Test coverage

The E2EE test harness (__test-e2ee__.ts) tests crypto primitives: key generation, export/import, key derivation, encrypt/decrypt round-trip, and room isolation. It does not test RoomClient integration (e.g., real key exchange between two RoomClient instances over WebSocket).

No automated tests exist for:
- RoomClient: key exchange, presence updates, sendMessage, reconnection
- RoomDO: presence broadcasts, key-exchange relay, peer-left on disconnect
- FoyerPage: POST /api/rooms, navigation
- RoomPage: RoomClient integration, UI updates, clipboard copy

The FEAT findings state "Manual two-tab test pending user verification" (FEAT-003) and "Manual browser test pending" (FEAT-004). These are acceptance criteria, not nice-to-haves. Without them, we don't know if the key exchange actually works in a real two-peer scenario.

## Not tested

- Simultaneous peer joins (race condition in key exchange ready check)
- Multi-peer rooms (>2 participants) — per-peer encryption not implemented
- WebSocket reconnection after disconnect
- Clipboard copy on browsers without Clipboard API
- Room expiry after 30 minutes (not implemented)
- Peer disconnect during key exchange (orphaned sharedKeys entries)
- Malformed messages from server (client crash risk)
- Server-side message validation (relay of invalid JSON)
- Key exchange with peer who never sends their public key (ready never fires)
- Browser tab close without disconnect() call (handled by browser WebSocket close, but state inconsistency in RoomClient if reconnect happens later)
