# M2: Rooms + E2EE + Presence + Invite (Pass 2)

This milestone implements secure room infrastructure with E2EE key exchange, presence broadcasting, and invite URLs. Room creation, WebSocket connections, ECDH P-256 key exchange with HKDF-SHA-256 derivation, AES-GCM-256 encryption, automatic reconnection, room expiry, message validation, and a waiting room UI are all complete.

All prior review findings (pass 1) have been addressed: reconnection logic with exponential back-off (FR-104), room expiry alarms (FR-103), message validation, WebSocket readyState constants, clipboard API fallback, deployment-compatible API URLs, and key exchange race condition fix. TypeScript compilation passes cleanly for web and edge packages.

**Verdict**: APPROVED

## High-level view

Reconnection implements exponential back-off per FR-104: delays start at 1s and double each attempt (1s, 2s, 4s, 8s…), capped at 30s, giving up after 5 minutes. RoomClient tracks reconnection state separately from connection state, preserves the ECDH key pair across reconnects, and resets the attempt counter on successful connection. Manual disconnection (calling disconnect() explicitly) prevents automatic reconnection.

Room expiry uses Durable Object alarms: the constructor sets a 30-minute alarm, every incoming message updates lastActivityAt and reschedules the alarm, and the alarm() handler checks elapsed time and closes all WebSockets if 30 minutes have passed. If activity occurred during the alarm window, the alarm reschedules itself. This matches FR-103's requirement for 30-minute inactivity cleanup.

The key exchange race condition is fixed by tracking expectedPeerCount: when peer-joined messages arrive, the client increments expectedPeerCount (but only for the initial batch), and a 50ms setTimeout marks initialPeerCountReceived as true, triggering checkReadyState(). The ready check now compares sharedKeys.size against expectedPeerCount instead of peers.length, eliminating the race where two peers check before seeing each other's peer-joined events.

Deployment compatibility changes: FoyerPage POSTs to /api/rooms (relative URL, not hardcoded localhost:8787), and RoomClient constructs WebSocket URLs using window.location.protocol and window.location.host, selecting wss:// for HTTPS and ws:// for HTTP.

Message validation in RoomDO checks message structure before relaying: type/roomId/peerId must be strings, key-exchange payloads must have peerId and publicKey with valid JWK structure (kty and crv strings). Invalid messages get an error response sent to the sender, not relayed to other peers.

## Reconnection state machine

The reconnection flow starts when the WebSocket onclose handler fires and checks three conditions: wasConnected (prevents reconnect if never connected), autoReconnect (global flag, currently always true), and !manualDisconnect (set when calling disconnect() explicitly). If all pass, scheduleReconnect() fires.

scheduleReconnect() initializes reconnectStartTime (if null), calculates elapsed time, gives up after 5 minutes, and schedules a setTimeout with delay = min(2^reconnectAttempts * 1000, 30000). The first attempt uses 2^0 = 1s, second 2^1 = 2s, third 2^2 = 4s, fourth 2^3 = 8s, fifth 2^4 = 16s, sixth and beyond 30s (capped).

On successful connection (onopen), the client resets reconnectAttempts and reconnectStartTime to null. This means if the connection stays up briefly then drops again, the exponential back-off restarts from 1s, not from where it left off. FR-104 doesn't specify whether back-off resets on brief success, so this is acceptable.

The keyPair is preserved across reconnections: connect() only generates a new key pair if this.keyPair is null. This prevents peers from needing to re-exchange keys if reconnecting to the same room within the 5-minute window.

## Room expiry timing and alarm rescheduling

The DO constructor calls setRoomExpiryAlarm(), which sets an alarm 30 minutes from now (Date.now() + 30 * 60 * 1000). When any message arrives, webSocketMessage updates lastActivityAt = Date.now() and calls setRoomExpiryAlarm() again. Cloudflare Durable Objects replace the existing alarm when setAlarm is called, so this continuously pushes the alarm 30 minutes into the future as long as messages arrive.

When the alarm fires, alarm() checks if Date.now() - lastActivityAt >= 30 minutes. If yes, it closes all WebSockets with code 1000 and reason "Room expired due to inactivity", then clears the sessions map. If no (activity occurred during the alarm window), it reschedules the alarm.

The "activity occurred during alarm window" case happens if a message arrives after the alarm is scheduled but before it fires. This is unlikely with a 30-minute window but possible if alarms are delayed. The reschedule prevents premature expiry.

FR-103 requires "rooms with no activity for 30 minutes are cleaned up." This implementation matches that requirement. The alarm does not delete the DO itself—Cloudflare evicts idle DOs automatically after a period (not documented precisely). The alarm's purpose is to close WebSockets and free memory, not to delete the DO instance.

## Key exchange race condition fix

The original implementation checked if (this.sharedKeys.size === this.peers.length) after each key-exchange. This failed when two peers connected simultaneously: Peer A connects, receives no peer-joined messages (no existing peers), derives zero keys, checks 0 === 0, signals ready. Peer B connects, receives peer-joined for A, adds A to peers, derives A's key, checks 1 === 1, signals ready. Both signal ready before exchanging keys.

The fix tracks expectedPeerCount separately from peers.length. When peer-joined messages arrive, the client increments expectedPeerCount only if initialPeerCountReceived is false. After the first peer-joined, a 50ms setTimeout sets initialPeerCountReceived = true and calls checkReadyState(). Subsequent peer-joined events (for new arrivals after the initial batch) don't increment expectedPeerCount.

The 50ms delay gives time for all initial peer-joined messages to arrive before marking the batch complete. This assumes the server sends all existing peers as individual messages in quick succession. If network latency exceeds 50ms, the batch could be incorrectly split. A more robust approach would be to send a "peer-list-complete" message from the server, but that adds protocol complexity.

checkReadyState() now checks if (this.sharedKeys.size === this.expectedPeerCount && this.connectionState === 'connected'). This ensures the client waits until it has keys for all peers present when it joined.

## Multi-peer encryption gap

sendMessage() includes this code:

```typescript
if (encrypt && this.connectionState === 'ready') {
  const payloadJson = JSON.stringify(payload);
  if (this.sharedKeys.size > 0) {
    const firstKey = this.sharedKeys.values().next().value;
    const encrypted = await encryptMessage(firstKey, payloadJson);
    finalPayload = encrypted;
  }
}
```

For a 2-peer room, Peer A and Peer B both derive the same shared key (ECDH symmetry). When A encrypts with their "firstKey," B can decrypt with their "firstKey" because the keys are identical.

For a 3-peer room, Peer A derives keys with B and C (two different keys), Peer B derives keys with A and C, Peer C derives keys with A and B. When A broadcasts an encrypted message using their first key (say, the A-B key), Peer B can decrypt it but Peer C cannot (C only has the A-C key, which is different).

The TODO(M3) comment acknowledges this and lists three approaches:
1. Per-peer encryption: encrypt the payload once per peer, send individual messages, add targetPeerId to the protocol so the server routes per-peer.
2. Hybrid encryption: generate a random session key (AES-256), encrypt the bulk payload once with the session key, encrypt the session key per-peer using each shared secret, send one message with N encrypted session keys + one encrypted payload.
3. Broadcast plaintext for non-sensitive data (presence, sync events), per-peer for sensitive data (chat, subtitles).

Approach 2 is standard for group messaging (Signal's Sender Keys, MLS, etc.). Approach 1 is simple but scales poorly (N messages for N peers). Approach 3 reduces encryption overhead but leaks sync events and subtitle timing to the server.

M2 scope is 2-peer rooms. Multi-peer is not a requirement until later milestones (if at all—requirements don't specify >2 viewers). This gap is acceptable for M2.

## Deployment compatibility and API URLs

FoyerPage now POSTs to /api/rooms (relative URL). When deployed, the browser resolves this relative to the current origin. In dev, the web app runs on localhost:5173 and the edge worker runs on localhost:8787. A relative URL would POST to localhost:5173/api/rooms, which doesn't exist.

The fix is to configure Vite to proxy /api and /ws to localhost:8787 in dev. The web package's vite.config.ts should include:

```typescript
server: {
  proxy: {
    '/api': 'http://localhost:8787',
    '/ws': {
      target: 'http://localhost:8787',
      ws: true,
    },
  },
}
```

Without this proxy config, the relative URLs will 404 in dev. The commit diff doesn't show vite.config.ts changes, so this may be missing.

RoomClient constructs the WebSocket URL using window.location.protocol and window.location.host. This works in both dev and production: in dev it becomes ws://localhost:5173/ws/..., which Vite proxies to ws://localhost:8787/ws/...; in production it becomes wss://matinee.example.com/ws/..., which the edge worker handles directly.

## Message validation scope

The validateMessage() function checks:
- msg is an object
- msg.type is a string
- msg.roomId is a string
- msg.peerId is a string
- For key-exchange: payload is an object, payload.peerId is a string, payload.publicKey is an object, publicKey.kty is a string, publicKey.crv is a string

This prevents type confusion attacks (sending a number as type) and missing-field crashes (accessing payload.publicKey.kty when publicKey is undefined). It does not validate:
- roomId matches the actual room (the DO doesn't track its own roomId)
- peerId matches the sender's attached Peer.id (could be spoofed)
- publicKey is a valid JWK (only checks kty/crv exist, not their values)
- Other message types (sync, chat, etc.) have valid payloads

The current validation is sufficient to prevent crashes from malformed messages. Spoofed peerId is not a security risk because the server overwrites msg.peerId with peer.id from the attachment before relaying. Invalid JWK values (e.g., kty: 'foo') will cause importPublicKey to throw on the recipient side, but that's caught in RoomClient's try-catch.
